# Phishing Testing Dashboard

Этот проект — небольшая веб‑панель для генерации **трек-беков** (трекинговых ссылок) на email-адреса и сбора статистики кликов по ним.

Он полезен для моделирования поведения рассылок, проверки клиенской обработки ссылок и демонстрации базовых техник трекинга.

---

## Основные возможности

- **Добавление email-адресов** вручную или из файла.
- **Генерация уникальной трекинговой ссылки** для каждого email.
- **Автоматическое хранение в SQLite** (таблицы `emails` + `clicks`).
- **Сбор статистики кликов**: сколько раз и по каким email нажимали.
- **Страница аналитики** с общими метриками.
- **Управление почтовыми учетными записями** (IMAP/POP3)
- **Отправка email-кампаний** с планированием, случайным распределением и мониторингом.

## Разделы интерфейса (по коду)

### Dashboard — `/`
**Файлы:**
- `templates/dashboard.html` — интерфейс и логика JS для таблицы кликов.
- `api.py` — маршрут `/api/clicks` возвращает записи кликов.
- `api.py` — маршрут `/api/delete` удаляет записи.
- `exports.py` — маршруты экспорта (Excel/CSV/SQL/SQLite).

**Что делает:**
- Загружает клики из `/api/clicks` и отображает их в таблице.
- Позволяет отмечать записи и удалять их через `/api/delete`.
- Предоставляет выгрузку кликов в разные форматы (кнопка «Скачать»).

### Email адреса — `/emails`
**Файлы:**
- `templates/emails.html` — интерфейс.
- `emails.py` — маршруты `/api/emails`, `/api/emails/delete`, `/api/emails/upload`.

**Что делает:**
- Добавляет email-адреса через форму (textarea) с POST на `/api/emails`.
- Показывает таблицу существующих email + трекинговые ссылки (данные берутся с `/api/emails`).
- Удаляет выбранные email (POST `/api/emails/delete`).
- Реализует drag’n’drop:
  - `.txt`/`.csv` файлы разбираются прямо в браузере;
  - `.xlsx`/`.xls` отправляются на сервер в `/api/emails/upload` и разбираются через `pandas`.

### Почтовые учетные записи — `/mail-accounts`
**Файлы:**
- `templates/mail_accounts.html` — интерфейс.
- `mail_accounts_api.py` — маршруты `/mail-accounts`, `/api/mail-accounts/add`, `/api/mail-accounts/list`, `/api/mail-accounts/test/<id>`, `/api/mail-accounts/delete/<id>`.

**Что делает:**
- Управляет IMAP/POP3 учетными записями отправителя.
- Позволяет добавить аккаунт, автоматически заполнить параметры популярных сервисов.
- Тестирует подключение к почтовому серверу.
- Отображает список сохранённых аккаунтов и их статус.
- Поддерживает массовое удаление.

### Отправка писем — `/mail-sender`
**Файлы:**
- `templates/mail_sender.html` — интерфейс.
- `mail_sender_api.py` — маршруты `/mail-sender` и API кампаний.

**Что делает:**
- Создаёт кампании для отправки писем.
- Планирует отправку на выбранное время и распределяет рассылку.
- Позволяет сохранять, загружать и удалять шаблоны писем.
- Использует список получателей из раздела Email адреса.
- Отслеживает статус рассылок и показывает уведомления о доставке.

### Аналитика — `/analytics`
**Файлы:**
- `templates/analytics.html` — интерфейс.
- `api.py` — маршрут `/api/analytics`.

**Что делает:**
- Загружает агрегированную статистику по кликам (общее число ссылок, кликов, процент кликов).
- Рисует прогресс-бар CTR и показывает дополнительные метрики.
- Предоставляет экспорт аналитики в несколько форматов.

## Как собирается и запускается (Docker)

### Сборка образа (Docker)

Основной сценарий — запуск `scripts/build.sh`.

Этот скрипт выполняет точные действия (строки указаны для текущей версии проекта):
- задаёт дефолтные значения (строки 6–9): `DEFAULT_SECRET`, `DEFAULT_SECURE`, `DEFAULT_ADMIN`, `DEFAULT_PASS`.
- задаёт тег образа (строка 12): `IMAGE_TAG='1.0.1'`.
- запрашивает у пользователя параметры (строки 14–25):
  - `SECRET_KEY` (строка 14);
  - `SESSION_COOKIE_SECURE` (строка 17);
  - `ADMIN_USER` (строка 20);
  - `ADMIN_PASS` (строка 23).
- собирает образ через `docker build` (строки 30–35) и передаёт параметры как `--build-arg`.
- сохраняет результаты в `.build_defaults` (строки 42–50) для последующих обновлений.

Ручная сборка (без скрипта):

```bash
docker build -t phishing-dashboard:1.0.1 .
```

### Переменные окружения и сборка

В `Dockerfile` (строки ~6–20) определены аргументы и экспортируются в `ENV`:
- `ARG SECRET_KEY=phishing-dashboard-2026-super-secret-key` → `ENV SECRET_KEY=${SECRET_KEY}`
- `ARG SESSION_COOKIE_SECURE=False` → `ENV SESSION_COOKIE_SECURE=${SESSION_COOKIE_SECURE}`
- `ARG ADMIN_USER=admin` → `ENV ADMIN_USER=${ADMIN_USER}`
- `ARG ADMIN_PASS=passwd123` → `ENV ADMIN_PASS=${ADMIN_PASS}`

Эти переменные доступны приложению через `os.environ`.

### Запуск контейнера

Запуск с сохранением базы данных на хосте (рекомендуется):

```bash
docker run -d -p 8080:8080 --name phishing-dashboard \
  -v "$PWD/phishing_data.db:/app/phishing_data.db:rw" \
  phishing-dashboard:1.0.1
```

`phishing_data.db` хранит все email, токены и клики. Монтирование позволяет сохранять данные между перезапусками.

### Обновление проекта

Скрипт `scripts/update.sh` (строки 1–160) автоматизирует обновление:
- делает `git pull`;
- читает значения из `.build_defaults` (если файл есть) и использует их как значения по умолчанию;
- при наличии запущенного контейнера определяет текущие env-переменные (`SECRET_KEY`, `ADMIN_USER`, `ADMIN_PASS`);
- если файл `phishing_data.db` отсутствует на хосте, копирует его из контейнера;
- пересобирает образ с теми же значениями (через `docker build --build-arg ...`);
- останавливает и удаляет старый контейнер;
- запускает новый контейнер, снова монтируя `phishing_data.db`.

## Переменные, которые влияют на запуск (файлы и строки)

### Где задаются значения при сборке

- `scripts/build.sh` (строки 6–25):
  - Строки 6–9 задают дефолтные значения (`DEFAULT_SECRET`, `DEFAULT_SECURE`, `DEFAULT_ADMIN`, `DEFAULT_PASS`).
  - Строка 12 задаёт тег образа `IMAGE_TAG='1.0.1'`.
  - Строки 14–25 запрашивают у пользователя `SECRET_KEY`, `SESSION_COOKIE_SECURE`, `ADMIN_USER`, `ADMIN_PASS`.
  - Строки 30–35 передают их в `docker build --build-arg ...`.
  - Строки 42–50 сохраняют данные в `.build_defaults`.

- `scripts/update.sh` (строки 15–63):
  - Строки 16–20 задают жёсткие значения по умолчанию (`default_secret`, `default_secure`, `default_admin`, `default_pass`, `default_image_tag`).
  - Строки 22–31 читают `.build_defaults` (если файл существует) и подставляют значения.
  - Строки 54–61 запрашивают у пользователя `SECRET_KEY`, `SESSION_COOKIE_SECURE`, `ADMIN_USER`, `ADMIN_PASS` (с использованием значений по умолчанию).
  - Строки 81–89 и 95–103 отвечают за пересборку образа и рестарт контейнера.

### Где переменные используются/читаются внутри контейнера

- `Dockerfile` (строки 6–16): определяет `ARG` и экспортирует их в `ENV`.
- `config.py` (строки 1–30): читает `SECRET_KEY` и `SESSION_COOKIE_SECURE` из окружения и формирует конфигурацию Flask.
- `db.py` (строки 20–60): при первом запуске создаёт администратора, читая `ADMIN_USER` и `ADMIN_PASS` из окружения.

## Техническая структура

### Backend (Flask)
- `main.py` — точка входа, подключает роуты и middleware (CSRF, сессии).
- `emails.py` — обрабатывает:
  - загрузку email из textarea (`/api/emails`);
  - загрузку `.xlsx`/`.xls` через `pandas` (`/api/emails/upload`);
  - удаление email (`/api/emails/delete`).
- `api.py` — возвращает данные кликов и аналитику.
- `db.py` — инициализирует базу и создает админа при первом запуске.

### UI (HTML + JS)
- `templates/emails.html` — страница управления email:
  - drag’n’drop файл-обработчик;
  - зона ввода списка;
  - таблица с трекерами.
- `templates/dashboard.html` — общий обзор статистики.
- `templates/analytics.html` — список всех кликов.

## Как работают файлы с email

### `.txt` / `.csv`
Обрабатываются прямо в браузере: содержимое читается как текст и вставляется в textarea.

### `.xlsx` / `.xls`
Отправляются на сервер в маршрут `/api/emails/upload`.
Сервер разбирает таблицу через `pandas.read_excel`, извлекает из ячеек email (в т.ч. несколько в одной ячейке) и добавляет их в базу.

## Где меняются ключевые переменные (файлы + строки)

Если вы не используете скрипты установки (`build.sh`/`update.sh`), то **эти файлы** — места, где можно вручную изменить ключевые параметры.

### Где задаются значения (скрипты)

#### `scripts/build.sh`
- Файл: `scripts/build.sh`.
- Здесь запрашиваются значения:
  - `SECRET_KEY` (строка 14)
  - `SESSION_COOKIE_SECURE` (строка 17)
  - `ADMIN_USER` (строка 20)
  - `ADMIN_PASS` (строка 23)
- Значения передаются в `docker build --build-arg ...` (строки 30–35).
- Также сохраняются в `.build_defaults` (строки 42–50).

#### `scripts/update.sh`
- Файл: `scripts/update.sh`.
- Он читает значения из `.build_defaults` (строки 22–31).
- Запрашивает те же параметры у пользователя (строки 54–61), но значения можно задать вручную изменением `.build_defaults`.

### Где параметры реально используются в контейнере

#### `Dockerfile`
- Файл: `Dockerfile`.
- Здесь задаются аргументы сборки и экспортируются в окружение:
  - `ARG SECRET_KEY` → `ENV SECRET_KEY` (строки 7–13).
  - `ARG SESSION_COOKIE_SECURE` → `ENV SESSION_COOKIE_SECURE` (строки 8–14).
  - `ARG ADMIN_USER` → `ENV ADMIN_USER` (строки 9–15).
  - `ARG ADMIN_PASS` → `ENV ADMIN_PASS` (строки 10–16).

> Чтобы изменить значение `SECRET_KEY`/`ADMIN_PASS` без скриптов, можно подать их через `docker build --build-arg ...` или напрямую в `docker run -e ...` (но тогда надо изменить Dockerfile/скрипты, чтобы не затирать).

#### `config.py`
- Файл: `config.py`.
- Здесь читаются переменные окружения:
  - `SECRET_KEY` (строки 8–10)
  - `SESSION_COOKIE_SECURE` (строка 25)

Если нужно изменить эти значения без сборки, установите их в окружении контейнера (`-e SECRET_KEY=...`).

#### `db.py`
- Файл: `db.py`.
- При первом запуске создаётся администратор, используя:
  - `ADMIN_USER` и `ADMIN_PASS` из окружения (строки 29–32).

Чтобы изменить логин/пароль администратора вручную, можно либо:
- изменить `ADMIN_USER`/`ADMIN_PASS` в окружении (Docker `-e`), либо
- напрямую обновить запись в таблице `users` (SQLite `phishing_data.db`).
